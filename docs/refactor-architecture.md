# Архитектура и правило разработчика для переписывания кода

Зафиксировано 20.11.2026 по методу Димы Зыкова: перед тем как давать агенту задачу «проверь и перепиши код», архитектура объявляется явно, и у агента уже описано правило «python backend разработчик».

## Объявление архитектуры (даётся агенту перед задачей)

> Перепиши код согласно документации (`docs/business-requirements/`, `human-requirements.txt`), на основе текущего кода, используя **pywebview (WebView2 на Windows, WebKit на macOS, Qt WebEngine на Linux) + MVVM + паттерн «Сигналы и слоты»**.

Расшифровка слоёв для этого проекта:

- **View** — веб-интерфейс (HTML/JS/CSS в окне pywebview; статика и `/ui/*` отдаёт python-сервер).
- **ViewModel** — `mnema/http_router.py` (маршруты + схемы) и `js_api` (`App.Api` в `desktop.py`): единая точка, через которую View получает данные и команды.
- **Model** — домен и application: `memory.py`, `vault.py`, `chat/` (`chat/engine.py`, `chat/tools.py`, `chat/planner.py`), пакет `learn/`, `locks.py` и т.д. View не обращается к Model напрямую.
- **Сигналы и слоты** — события как сигналы, подписки как слоты: JS вызывает `pywebview.api.*` (слот), обратно Python шлёт события через `window.evaluate_js` и HTTP-ответы; View подписывается и обновляет себя. Связь строго через эти сигналы, без прямых вызовов UI из домена.

Правила применения:

- Поведение менять только там, где этого требует документация; остальное — 1:1 с текущим кодом.
- Новые runtime-зависимости — только с явного одобрения владельца.
- Никаких коммитов в git без команды владельца. Это переопределяет AGENTS.md («каждая правка — отдельный коммит»): в BRD-сессиях владельца коммиты только по его прямой команде.

## Правило: python backend разработчик

- Ты — python backend разработчик: пишешь только backend (Python) и не принимаешь продуктовых решений.
- Единственный источник требований — документация BRD (`docs/business-requirements/` и `human-requirements.txt`). Если код противоречит документации — не меняй требования молча: зафиксируй вопрос и сообщи владельцу.
- Работай по объявленной архитектуре (pywebview + MVVM + «Сигналы и слоты»), слои transport → application → domain; domain не переписывается без отдельного задания.
- Стиль — как в текущей кодовой базе (короткие функции, docstring на английском в стиле модуля, типы где они уже есть); `ruff check`, `ruff format --check` и `prettier --check` — чисто.
- MCP-правила AGENTS.md не ломать: `mcp_call`/`mcp_smoke*` — всегда FORCE_ASK, никакого автоматического sweep по подстроке; deny-list путей (`.ssh`, `.gnupg`, `.aws`, keyring, browser secret stores) не расширять.
- Каждое изменение — с тестами; полный прогон (`python3 -m unittest discover -s tests -p "test_*.py"`) зелёный: допустимы только известные средовые падения (текущие 3) и skipped.
- Маленькие шаги: перенёс ветку → прогнал тесты → дальше. Не переписывай работающее без причины, не добавляй TODO и мусор.
- Отчёт владельцу: изменённые/созданные файлы, результат прогона (Ran/FAILED/skipped), ruff/prettier-статус, git-состояние (ветка, HEAD, `git status --short`), что осталось старым и почему.

## План переписывания: 5 частей (после каждой — перепроверка)

Каждая часть — отдельный контекст-агент, приёмка тестами + ruff/prettier, затем критика; владелец может остановиться и перепроверить между частями. Все части работают по объявленной архитектуре и правилу выше.

1. **Инвентаризация: код ↔ BRD.** Без изменений кода. Матрица «BP/FR ↔ модули, маршруты, js_api», список расхождений код↔документы с файл:строка, приоритезация. Результат — документ (вне репозитория), критик проверяет полноту и правдивость каждой строки.
2. **Транспорт/ViewModel.** `http_router.py` + `http_schemas.py` доводятся до полного покрытия BRD: закрываются дельты из части 1, контракты ответов по FR. Приёмка: полный прогон зелёный (3 средовых + skipped), контрактные тесты на каждый закрытый маршрут.
3. **UI-мост MVVM (сигналы и слоты).** `desktop.py`/`js_api` и View: единый механизм сигналов в обе стороны (события Python → View через `evaluate_js`, команды View → Python через `pywebview.api.*`), состояние — только в ViewModel; визуал не меняется. Приёмка: живой запуск, ключевые сценарии UI не сломаны, тесты.
4. **Поведение по решениям BRD.** Внести в код зафиксированные решения владельца (пресеты Quality, журнал 10 МБ/5 архивов, recovery-ключ, экспорт чата Markdown, экспорт при шифровании запрещён, лимит записи 5 часов, 100 МБ, кулдаун 10 минут, синк-расписание 10/5 минут, «открой этот сайт» и т.д.) — строго по документам, ничего сверх них. Приёмка: тест на каждое решение + полный прогон.
5. **Регрессия и финальная критика.** Полный прогон, ruff/prettier, живые проверки (`/api/ping`, визард, чат, память), финальный отчёт: git-состояние, что переписано/осталось старым и почему. Критик проходит всю цепочку частей 1–5 на согласованность с BRD и архитектурой.

## Цель переписывания: отделить морду от бэкенда

Главная цель пяти частей — развести UI и backend так, чтобы интерфейс можно было заменить целиком (другой фронтенд или другой движок окна), не переписывая backend. Критерий готовности: View общается с backend ТОЛЬКО через ViewModel (HTTP-контракт `http_router.py` + `js_api`), backend не знает о DOM и не содержит разметки; состояние живёт в ViewModel, а не в DOM; UI-события и обновления идут только через «Сигналы и слоты».

План именно этой задачи (как ложатся на 5 частей):

1. **Инвентаризация связок (часть 1).** Найти все места, где UI и backend связаны напрямую: inline-JS в Python (строки `evaluate_js` с кусками разметки/скриптов), разметка внутри `desktop.py`/`api.py`, чтение DOM из Python, состояние, продублированное в DOM и Python, прямые вызовы сервера мимо роутера. Результат — карта связок с файл:строка и списком, что куда переносится.
2. **Единый контракт ViewModel (часть 2).** Все данные и команды для View — через `http_router`/схемы и `js_api`; у каждой операции — схема ответа; убрать обходные пути. Приёмка: контрактные тесты, полный прогон.
3. **Вынос View в отдельный модуль (часть 3).** Вся разметка/стили/скрипты View — в выделенную папку (сейчас статика + вшитые куски), без бизнес-логики; Python отдаёт только файлы и данные. `desktop.py` оставляет только окно и мост: JS → `pywebview.api.*` (слоты), Python → `evaluate_js`-события (сигналы), никаких логических ветвлений по состоянию UI в Python.
4. **Сигналы и слоты до конца (часть 3, продолжение).** Каждое обновление UI — событие-сигнал из ViewModel, каждый ввод — слот; состояние одного места (ViewModel), View — чистая проекция. Проверка: запуск backend без окна (headless, только HTTP) выполняет все сценарии.
5. **Проверка отдирания (часть 4–5).** Поведенческие решения BRD вносятся только после развода; регрессия + «замещаемость интерфейса»: все ключевые сценарии проходят через HTTP-контракт без окна; финальная критика всей цепочки.
